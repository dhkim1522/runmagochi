# phase

> `docs/roadmap.md` 의 페이즈 하나를 구현 계획 → 테스트 우선 구현 → 자동 검증 → 문서 갱신까지 한 번에 진행한다. 모든 출력은 한국어로 짧게 쓴다.

## 인자

`$ARGUMENTS` 를 읽는다.

- `--auto`: 자동 모드. 계획 승인과 중간 질문을 건너뛴다. 없으면 수동 모드.
- 숫자: 진행할 페이즈 번호. 없으면 현재 위치에서 정한다.

## 규칙

- 원천 문서는 `docs/` 다. 범위·완료 기준은 `docs/roadmap.md`, 동작 규칙은 `docs/specs/`, 구조는 `docs/architecture.md`, 화면은 `docs/screens.md` 를 따른다.
- 문서와 다르게 구현해야 하면 멈추고 묻는다. 자동 모드에서는 문서대로 구현하고 차이를 계획 파일 "자동 결정" 에 남긴다.
- 테스트가 통과한 상태로만 커밋한다. 작업 하나가 끝날 때마다 `main` 에 커밋하고 push한다.
- `--force` push, 기록 되돌리기(`reset --hard`, `rebase -i`), 브랜치 삭제는 하지 않는다.
- 새 기술 결정(패키지 추가·교체, 구조 변경)은 `docs/decisions/` 에 다음 번호로 기록한다. 자동 모드에서 내린 결정은 상태를 `자동 채택 (검토 필요)` 로 적는다.
- 사람이 해야 하는 완료 기준(실기기 러닝, 지인 베타 의견)은 자동 모드에서도 통과 처리하지 않는다.

## 0. 준비

1. `git status` 가 깨끗한지 확인한다. 커밋 안 된 변경이 있으면 멈추고 알린다. 자동 모드도 멈춘다.
2. `git pull --rebase` 로 최신 상태를 받는다.
3. `HANDOFF.md`, `docs/roadmap.md` 를 읽는다.

## 1. 페이즈와 상태 확인

1. 진행할 페이즈 번호를 정한다.
   - 인자로 받은 번호
   - 없으면 `docs/roadmap.md` "현재 위치" 의 페이즈. 페이즈 0이거나 현재 페이즈가 완료됐으면 다음 페이즈
2. `docs/plans/phase-<번호>.md` 를 읽는다. 상단 "상태" 값으로 다음 단계를 고른다.

| 계획 파일 | 상태 | 다음 단계 |
| --- | --- | --- |
| 없음 | | 2. 계획 |
| 있음 | 계획 | 3. 승인 |
| 있음 | 실행 | 4. 실행 (체크되지 않은 첫 작업부터) |
| 있음 | 검증 | 5. 자동 검증 |
| 있음 | 실측 대기 | 7. 완료 판정 |
| 있음 | 완료 | 다음 페이즈로 1번부터 |

3. 진행할 페이즈, 현재 상태, 모드를 한 줄로 알린다.

## 2. 계획

`superpowers:writing-plans` 스킬로 구현 계획을 쓴다. 저장 위치는 `docs/plans/phase-<번호>.md` 다.

입력:
- `docs/roadmap.md` 해당 페이즈의 범위와 완료 기준
- 범위에 걸린 요구사항(`docs/product.md`), 명세(`docs/specs/`), 구조(`docs/architecture.md`), 화면(`docs/screens.md`)
- 와이어프레임 이미지 `design/wireframes/png/`
- Flutter 구조는 `dart-flutter:flutter-apply-architecture-best-practices` 를 따른다.

계획 파일 형식:

```
# 페이즈 <번호> 구현 계획

- 상태: 계획
- 모드: 수동 | 자동
- 범위: docs/roadmap.md 페이즈 <번호>

## 작업
- [ ] 1. <작업 이름>
  - 파일: <만들거나 고칠 파일>
  - 테스트: <먼저 작성할 테스트>
  - 확인: <통과를 확인할 명령>
...

## 완료 기준
### 자동 확인
- [ ] <명령으로 확인할 항목>
### 사람 확인
- [ ] <실기기 실측 등>

## 자동 결정
<자동 모드에서 내린 결정과 근거. 없으면 "없음">
```

작업은 한 번에 커밋할 수 있는 크기로 나눈다. 계획을 커밋하고 push한다.

## 3. 승인

- **수동 모드**: 작업 목록과 완료 기준을 요약해 보여주고 `AskUserQuestion` 으로 승인·수정을 묻는다. 수정 요청이 오면 계획을 고치고 다시 묻는다.
- **자동 모드**: 건너뛴다.

승인되면 상태를 `실행` 으로 바꾸고 커밋한다.

## 4. 실행

`superpowers:subagent-driven-development` 로 체크되지 않은 작업을 순서대로 진행한다. 작업마다:

1. `superpowers:test-driven-development` 를 따라 테스트를 먼저 작성하고 실패를 확인한다.
2. 구현해 테스트를 통과시킨다.
3. `dart analyze` 와 `flutter test` 를 통과시킨다.
4. `superpowers:requesting-code-review` 로 리뷰하고 지적을 반영한다.
5. 계획 파일에서 작업을 체크하고, 코드와 함께 커밋·push한다.

막힘 처리:
- 같은 실패를 3번 고쳐도 통과하지 못하면 `superpowers:systematic-debugging` 으로 원인을 찾는다.
- 그래도 해결되지 않으면 멈춘다. 계획 파일에 막힌 지점과 시도한 내용을 적고, 커밋·push하고 사용자에게 알린다. 자동 모드도 같다.

모든 작업이 체크되면 상태를 `검증` 으로 바꾼다.

## 5. 자동 검증

`superpowers:verification-before-completion` 을 따른다. 결과를 실제 명령 출력으로 확인하기 전에는 통과라고 쓰지 않는다.

- `flutter test`, `dart analyze`
- `flutter build apk --debug`
- 계획의 "자동 확인" 항목
- 에뮬레이터가 실행 중이면 앱을 띄워 핵심 흐름을 확인한다. 실행 중이 아니면 건너뛰고 그 사실을 적는다.

실패하면 4번으로 돌아가 고친다. 모두 통과하면 계획 파일에 체크한다.

## 6. 정리

1. 상태를 `실측 대기` 로 바꾼다.
2. `docs/roadmap.md` "현재 위치" 를 "페이즈 <번호> 구현 완료, 사람 확인 대기" 로 고친다.
3. `HANDOFF.md` 를 현재 상태와 다음 할 일(사람 확인 항목)로 교체한다.
4. 커밋하고 push한다.
5. 사람 확인 체크리스트와 디버그 APK 경로를 보여주고 끝낸다. 다음에 `/phase` 를 다시 실행하면 완료 판정을 한다고 알린다.

## 7. 완료 판정

사람 확인 항목마다 결과를 `AskUserQuestion` 으로 묻는다. 자동 모드에서도 묻는다.

- **모두 통과**
  1. 계획 파일 상태를 `완료` 로 바꾼다.
  2. `docs/roadmap.md` "현재 위치" 를 다음 페이즈로 고친다.
  3. `HANDOFF.md` 를 갱신하고 커밋·push한다.
  4. 다음 페이즈를 시작할지 묻는다. 자동 모드면 바로 1번부터 진행한다.
- **실패 항목 있음**: 실패 내용을 계획 파일에 새 작업으로 추가하고 상태를 `실행` 으로 바꾼 뒤 4번으로 간다.
