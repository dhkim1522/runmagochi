# playbook

> 러닝 + 도트 육성 앱(런마고치)을 8일 동안 만들며 얻은 진행 순서. 원본 문서는 이 저장소의 `docs/playbook.md` 이고 이 스킬은 요약이다. 모든 출력은 한국어로 짧게 쓴다.

## 쓰는 법

1. 인자로 프로젝트 설명을 받는다. 없으면 한 줄로 묻는다.
2. 아래 "순서"를 그 프로젝트에 맞춰 로드맵 초안(`docs/roadmap.md`)으로 옮긴다. 페이즈마다 범위와 완료 기준(자동·E2E·사람)을 적는다.
3. "먼저 정할 것"을 사용자에게 한 번에 묻고 결정 기록으로 남긴다.
4. 만들 산출물 목록과 순서를 보여 주고 승인을 받는다. 승인 전에는 코드를 쓰지 않는다.

## 먼저 정할 것 (질문 목록)

- 목표 한 줄, 대상 사용자, 성공 기준(숫자)
- **가장 위험한 기능** 하나와 그것을 재는 기준
- 플랫폼 범위(Android/iOS/웹)와 출시 시점. 두 플랫폼이면 처음부터 정한다
- 로컬 우선인가, 서버가 필요한가
- 범위 밖으로 둘 것

## 순서

| 단계 | 산출물 | 완료 기준 |
| --- | --- | --- |
| 기획·조사 | 기획서(요구사항 ID, MVP 여부, 범위 밖), 시장조사 | ID 와 범위 밖이 있다 |
| 구조·로드맵 | 설계서(스택·구조·데이터 모델), 로드맵, 결정 0001 | 페이즈별 완료 기준이 있다 |
| 화면 콘티 | 와이어프레임, 화면 이동 흐름 | 화면마다 행동 하나 |
| 작업 환경 | 버전 고정, 개발 도구 목록, 인계 문서(`HANDOFF.md`) | 새 PC 에서 이어서 할 수 있다 |
| 코어 | 가장 위험한 기능 + 단위 테스트 | 실기기에서 기준을 쟀다 |
| 핵심 루프 | 다시 돌아올 이유(성장·보상) | 지인 의견 수집 |
| 기본 디자인 | 토큰 한 파일, 시안, 임시 에셋 | 사용자 승인 |
| 기능 확장 | 완성도 → 보상 → 부가 기능 | 페이즈마다 E2E |
| 디자인 완성 | 후보 3개 비교 → 선택 → 디자인 시스템·에셋 | 관문 3개(에셋·방향·품질) 승인 |
| 두 번째 플랫폼 | 빌드·권한·백그라운드·설치 | 본인 기기 실행 |
| 산출물 정리 | PRD·시나리오·화면설계서·아키텍처·ERD·시퀀스·결정 색인·개발 기록·README·플레이북 | 코드와 맞다 |
| 실기기 테스트 | 실측 기록, 개선 리포트, 지인 베타 | 기준 통과 |
| 출시 | 스토어 자료, 심사 | 출시할지 사용자가 정한다 |

## 규칙

- 원천은 저장소 문서다. 결정이 바뀌면 문서를 고친다.
- 페이즈는 계획 파일로 관리한다. 사람이 해야 하는 확인은 자동으로 통과시키지 않는다.
- 작업마다 테스트 먼저, 통과 상태로만 커밋·push, 끝날 때마다 인계 문서를 갱신한다.
- 결정은 번호 파일(배경·결정·결과)로 남기고, 앞선 결정을 바꾸면 이전 결정에 "대체됨"을 적는다.
- 문서의 숫자·이름은 코드에서 읽어 쓴다. 기억으로 쓰지 않는다.
- 다이어그램은 코드와 대조 테스트가 가능하게 만든다(ERD ↔ DB 정의, 토큰 ↔ 테마).

## 피할 실수

- 두 번째 플랫폼을 "나중에"로 미뤄 계획을 여러 번 고치기 → 처음부터 정한다.
- 실기기 확인을 계속 미루기 → 코어 직후 한 번 잰다. 에뮬레이터는 위치 필터를 달리 걸러 못 보는 것이 있다.
- 보상 규칙을 만든 뒤 뒤집기 → 만들기 전에 시나리오 표로 지인에게 묻는다.
- 이상 기록을 설명 없이 끝내기 → 기록은 살리고 보상만 조절하며 이유를 보여 준다.
- 단위 테스트만 믿기 → 페이즈 검증에 E2E 를 넣는다. 에뮬레이터 설정(시간대·권한)을 목록으로 둔다.
- 디자인을 한 번에 끝내려 하기 → 기본(토큰 한 파일)과 완성(교체)으로 나눈다.
- 화면설계서를 디자인 확정 전에 찍기 → 승인 뒤 한 번, 반복 촬영은 스크립트로.
