# 프로젝트 플레이북

> 런마고치(러닝 + 도트 육성 앱)를 8일간 만들며 얻은 진행 순서. 다음 프로젝트에서는 산출물을 먼저 만들고, 같은 곳에서 겪은 일을 되풀이하지 않도록 쓴다. 같은 내용을 프로젝트 스킬 [`playbook`](../.claude/skills/playbook/SKILL.md)로도 만들었다. 예시는 모두 이 저장소의 실제 파일이다 (2026-10-23).

## 한 장 요약

1. 아이디어를 **기획서 + 시장조사**로 굳히고, 요구사항에 ID 를 붙인다.
2. **가장 위험한 한 가지**(여기서는 백그라운드 GPS 기록)를 먼저 만들어 실기기에서 확인한다. 나머지는 그 위에 얹는다.
3. 기술 결정·범위 결정은 그때그때 **결정 기록**으로 남긴다.
4. 디자인은 **기본 → 완성** 두 단계로 나누고, 사람이 고르는 관문을 둔다.
5. 문서와 코드는 **자동으로 맞는지 확인**한다(테스트·대조).
6. 각 페이즈 끝에 **E2E + 인계 문서**를 갱신한다.
7. 출시 여부는 **직접 써 본 뒤** 정한다.

## 지킬 규칙

- **원천은 저장소 문서**: 결정이 바뀌면 문서를 고치고, 다른 곳(채팅·CLAUDE.md)에는 위치만 둔다 ([결정 0002](decisions/0002-docs-in-repo.md)).
- **페이즈는 계획 파일로 관리**: 작업 목록·테스트·확인 명령·완료 기준(자동·E2E·사람)을 한 파일에 둔다. 사람이 해야 하는 확인은 자동으로 통과시키지 않는다.
- **작업마다 테스트 먼저, 커밋·push**: 테스트가 통과한 상태로만 커밋한다.
- **결정은 번호 파일로**: 배경·결정·결과 3칸. 앞선 결정을 바꾸면 이전 결정의 상태에 "대체됨"을 적는다 ([색인](decisions/README.md)).
- **작업을 마칠 때마다 인계 문서 갱신**: 다른 PC 나 다음 세션이 바로 이어서 할 수 있게.
- **문서의 숫자·이름은 코드에서 읽어 쓴다**: 기억으로 쓰지 않는다. 이 프로젝트에서도 시퀀스를 쓰다 낡은 규칙(빠른 이동 자동 종료)을 그대로 적은 걸 코드를 읽고 바로잡았다.
- **다이어그램은 코드와 대조 가능한 것을 만든다**: ERD 는 DB 정의와 테스트로 대조([데이터 모델](data-model.md)), 색 토큰은 `tokens.json` 과 테마 테스트로 대조([theme_test](../test/core/theme_test.dart)).

## 이 프로젝트에서 겪은 일과 다음에는

| 겪은 일 | 비용 | 다음에는 |
| --- | --- | --- |
| iOS 시점이 네 번 바뀜 (0005 → 0014 → 0017 → 0030) | 계획 문서·페이즈 번호를 여러 번 고침 | 두 플랫폼이 목표면 **처음부터** 정하고, 코어 페이즈에서 두 플랫폼 빌드가 돌게 한다 |
| 실기기 확인을 "나중"으로 미룸 (0017 → 0026 → 0035) | 페이즈 1~6 의 사람 확인이 쌓였다 | 위치·센서 앱은 **코어 직후** 실기기로 기준값을 한 번 잰다. 에뮬레이터는 위치 필터를 달리 걸러 못 보는 것이 있다 |
| 주간 목표를 만들고 뺌 (0018) | 홈·온보딩·알림·보너스까지 걷어 냄 | 보상 규칙은 만들기 전에 시나리오 표로 지인에게 먼저 묻는다 |
| 빠른 이동 자동 종료가 버스·지하철에서 설명 없이 종료 (0033) | 규칙 재설계 | 이상 처리는 "**기록은 살리고 보상만 조절**, 이유를 보여 준다"로 시작한다 (0016 원칙) |
| 단위 테스트가 못 잡은 결함이 E2E 에서 나옴 (위치 복구, 알림 번호 겹침, 시간대 별칭) | 페이즈마다 1~4건 | 페이즈 검증에 E2E 를 반드시 넣고, 에뮬레이터 설정(시간대·권한)을 목록으로 둔다 ([개발 기록](dev-log.md)) |
| 디자인 방향을 두 번 고름 (말랑 클레이 → 연두) | 시안·토큰·화면 재작업 | 기본 디자인(2.5)은 값을 **토큰 한 파일**에 몰아 두어 교체만 하게 한다 (0010, 실제로 이 덕에 작업이 줄었다) |
| 화면설계서를 한 번 찍고 디자인이 바뀌어 여러 번 재촬영 | 촬영 작업 반복 | 설계서는 디자인 승인 **뒤**에 한 번 찍는다. 반복 촬영은 스크립트로 |
| 문서가 개발 중 계속 고쳐져 낡음 | 산출물 정리 페이즈가 필요했다 | 요구사항 ID·결정 번호·스키마 판처럼 **다른 문서가 가리키는 값**은 한 곳에서만 관리한다 |

## 새 프로젝트 시작 체크리스트

- [ ] 기획서: 목표 한 줄, 대상, 성공 기준(숫자), 요구사항 ID 표, 범위 밖
- [ ] 가장 위험한 기능을 하나 골랐고, 실기기로 재는 기준이 있다
- [ ] 플랫폼 범위(Android/iOS)와 출시 시점을 결정 기록에 적었다
- [ ] 저장소에 `docs/`, `docs/decisions/`, `docs/plans/`, `HANDOFF.md` 를 만들었다
- [ ] 버전 고정, 개발 도구 목록, 계정·폴더 분리 규칙을 `CLAUDE.md` 와 `docs/tooling.md` 에 적었다
- [ ] 로드맵: 페이즈마다 범위·완료 기준(자동·E2E·사람)을 적었다
- [ ] 로컬 우선인지, 서버 이전 경로가 있는지 설계서에 적었다
- [ ] 페이즈 0 끝에 와이어프레임과 화면 이동 흐름이 있다
