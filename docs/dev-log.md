## 개발 방식

- **페이즈 계획**: `docs/roadmap.md` 의 페이즈마다 `/phase` 가 계획 파일을 만든다. 작업을 한 번에 커밋할 크기로 나누고, 승인을 받은 뒤 순서대로 진행한다.
- **작업 하나의 흐름**: 실패하는 테스트 작성 → 구현 → `dart analyze`·`flutter test` 통과 → 리뷰 → 계획에 체크, 커밋, push.
- **서브에이전트**: 작업마다 구현 담당과 리뷰 담당을 나누고, 서로 다른 파일을 건드리는 작업은 둘씩 병렬로 진행했다(페이즈 3). 페이즈 끝에는 전체 리뷰를 한 번 더 했다.
- **에뮬레이터 E2E**: 페이즈 검증 마지막에 에뮬레이터로 시나리오를 직접 확인한다. 이 단계에서 단위 테스트가 못 잡은 결함이 나왔다(아래).
- **사람이 하는 것**: 디자인 관문(캐릭터 투표·UI 방향·출시 품질 승인), 실기기 러닝, 지인 베타 의견은 자동 모드에서도 통과 처리하지 않는다.

## 검증에서 잡은 결함

단위 테스트와 코드 리뷰를 통과했는데 에뮬레이터 E2E 나 화면설계서 촬영에서 나온 것들이다.

| --- | --- | --- |
| 2 | 위치 오류 뒤 기록이 복구되지 않음 | 오류·끊김 뒤 앱이 화면에 있으면 5초마다 다시 구독, 백그라운드면 앱 복귀 시 즉시 구독 |

## 규칙이 바뀐 곳

개발 중 요구가 바뀐 지점은 결정 기록에 남아 있다.

- **주간 목표 → 오늘 목표** (결정 0018): 주간 목표 카드·연속 주수·알림을 걷어 내고 시작 버튼 한 번으로 달리는 흐름으로. 기존 테이블 행은 남기고 새로 쓰지 않는다.
- **빠른 이동 자동 종료 → 탈것 의심 구간 빼기** (결정 0033): 팀 테스트(10-22)에서 버스·지하철을 타자 기록이 멈추거나 페이스가 튀고, 시속 30km 를 넘기면 설명 없이 끝났다. 30초 평균 시속 22km 초과 구간을 말풍선으로 알리며 빼고, 합계가 2분이면 종료.
- **iOS 시점**: 페이즈 3 → Android 먼저(0005·0014) → 출시 전에 붙임(0017) → 디자인과 나란히 일찍 시작(0030).
- **산출물과 실기기 순서**: 산출물 → 실기기(0022) → 실기기 → 산출물(0026) → 다시 산출물 → 실기기 테스트(0035). 실기기 테스트를 산출물 뒤로 미뤄 문서를 먼저 정리하고, 실측 결과로 바뀌는 부분만 고치기로 했다.
